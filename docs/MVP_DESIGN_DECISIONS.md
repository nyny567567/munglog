# MVP 설계 결정 기록

> 이 문서는 2026-09-15 설계 논의에서 확정한 MVP 방향을 기록한다. 구현·ERD·API
> 변경 작업을 지시하지 않으며, 기존 `기능정의서.md`, `ERD.md`, `API.md`를
> 삭제하거나 대체하지 않는다. 기존 문서와의 차이는 마지막 절에서 추적한다.

## 1. 도메인과 기록 경험

### 관계

핵심 관계는 **Member → Dog → Diary → DiaryPage**다. Diary는 Member 자체의 글이
아니라 특정 Dog의 일상 기록이며, 한 Dog는 같은 날짜에도 여러 Diary를 만들 수 있다.

이 관계는 기록의 주체를 명확히 하고, 시간이 쌓였을 때 Dog 단위로 추억을 탐색하게
한다. 별도 일반 Post를 만들지 않으며, 공개 Diary가 지역 피드의 원본 콘텐츠가 된다.

### DiaryPage

- 하나의 Diary는 **1~5개**의 DiaryPage를 가진다.
- 각 페이지는 하나의 미디어와 그 순간에 대한 선택적 글(`content`)으로 구성한다.
- MVP에서는 미디어가 이미지로 한정되므로 모든 페이지에 이미지가 필수이고, 본문은
  비어 있을 수 있다.
- `pageOrder`는 Diary 안에서 1부터 연속되고 중복될 수 없다.
- 장기 모델은 `objectKey`, `mediaType`, `content`, `pageOrder`다. `mediaType` enum은
  MVP에서 `IMAGE`만 갖고, 실제 동영상 지원 때 `VIDEO`를 추가한다.

페이지 순서를 대표 이미지와 상세 UI가 함께 사용하므로, 별도 썸네일 필드를 저장하지
않는다. `pageOrder = 1`의 이미지를 대표 이미지로 사용한다. 페이지 기반의 기록을
유지하면 사진 중심 카드와 아날로그 상세 화면을 같은 원본으로 제공할 수 있다.

### 상세와 지역 피드

- Diary 상세은 모든 DiaryPage를 순서대로 보여 주는 아날로그 일기 경험이다.
- 지역 피드는 Dog 정보, 기록 시각, 날씨, 첫 이미지, 첫 페이지 본문 일부, 페이지 수를
  담은 카드형 조회 DTO를 사용한다.
- Post나 피드 전용 중복 데이터를 만들지 않는다.
- MVP 피드 조회는 Diary 목록을 페이지 조회한 뒤 해당 Diary의 DiaryPage를 한 번에
  조회해 서비스에서 카드 DTO를 조립한다.

이 방식은 원본 데이터의 일관성을 지키고 초기 N+1 문제를 피한다. 데이터 규모가 커져
전용 projection이 필요해질 때만 최적화한다.

## 2. 시간과 지역

### 기록 시각

`diaryDate`와 `diaryTime`은 작성 시각이 아니라 **기록된 일상이 발생한 시각**이다.
작성 화면 진입 시 `Asia/Seoul` 기준 현재 날짜·시간을 기본값으로 주고, 과거 기록은
수정할 수 있다. 서버는 현재 시각보다 5분을 초과하는 미래 시각을 거절한다.

5분 허용은 브라우저와 서버의 시계 차이·입력 중 경과 시간을 흡수하면서 미래 시각으로
피드를 조작하는 일을 제한하기 위한 절충이다.

### Member 현재 지역과 Diary 공개 지역

- 회원가입 시 현재 활동 지역을 필수 입력한다.
- 지역은 상세 주소가 아닌 **시/군/구** 수준이며 `regionCode + regionName`으로 관리한다.
- Member의 지역은 현재 활동 지역이며 프로필에서 변경할 수 있다.
- 공개 Diary에는 공개 피드 귀속 지역을 별도 스냅샷으로 저장한다.
- `isPublic = true`인 Diary는 공개 지역 코드·이름을 반드시 가진다.
- `isPublic = false`인 Diary는 공개 지역 코드·이름을 모두 가지지 않는다.
- 비공개→공개와 재공개 때 Member의 현재 지역을 저장하고, 공개→비공개 때 스냅샷을
  제거한다.

이 정책은 이사 뒤에도 이미 공개된 기록이 당시의 지역 피드에 남도록 하며, 현재 활동
지역 기반의 미래 기능과 과거 공개 기록의 귀속을 혼동하지 않게 한다.

### 지역 피드

- 로그인·비로그인 모두 `regionCode`를 명시적으로 전달한다.
- Member의 현재 지역은 프론트엔드가 처음 선택할 지역을 제안하는 용도일 뿐, API의
  암묵적 기본값이 아니다.
- 정렬은 `diaryDate DESC, diaryTime DESC, diaryId DESC`다.
- MVP는 `page`, `size` 기반 offset 페이지네이션을 사용한다.
- `publishedAt`은 저장하지 않는다. 과거 기록의 공개·재공개가 피드 상단으로 올라오는
  것을 막고, '동네 강아지의 최근 일상'이라는 피드 의미를 지키기 위한 선택이다.

Cursor 페이지네이션과 무한 스크롤은 데이터 규모·UX 요구가 커질 때의 확장 후보다.

## 3. 공개, 삭제, 댓글 권한

### Soft Delete

Dog와 Diary는 각각 Soft Delete한다.

- Diary 개별 삭제는 Diary의 `deletedAt`으로 표현한다.
- Dog 삭제는 Dog의 `deletedAt`만 변경하며, 하위 Diary의 `deletedAt`을 일괄 변경하지
  않는다.
- 사용자에게 노출되는 모든 Diary는 **Diary와 연결된 Dog 모두 `deletedAt = null`**이어야
  한다.

Dog가 기록 묶음의 루트이므로 삭제된 Dog의 Diary는 개인 목록·상세·피드·댓글에서 모두
제외한다. Diary의 삭제 의미를 Dog 삭제와 분리해 두면, 향후 복구 정책을 검토할 때도
데이터 의미가 유지된다. Archive 상태는 YAGNI에 따라 MVP에서 만들지 않는다.

### 열람과 댓글

| 대상 | 비로그인 | 로그인 회원 | Dog 소유 Member |
| --- | --- | --- | --- |
| 공개 Diary·지역 피드 | 열람 가능 | 열람 가능 | 열람 가능 |
| 비공개 Diary | 열람 불가 | 열람 불가 | 열람·댓글 작성 가능 |
| 공개 + 댓글 허용 Diary | 댓글 열람 가능 | 댓글 열람·작성 가능 | 댓글 열람·작성 가능 |
| 공개 + 댓글 차단 Diary | 댓글 열람 가능 | 댓글 열람 가능, 신규 작성 불가 | 댓글 열람 가능, 신규 작성 불가 |

- 댓글 수정은 댓글 작성자만 가능하다.
- 댓글 삭제는 댓글 작성자 또는 해당 Diary의 Dog 소유 Member가 가능하다.
- `allowComments`를 true에서 false로 바꿔도 기존 댓글은 유지·열람 가능하며 신규
  댓글만 차단한다.
- 삭제된 Diary 또는 삭제된 Dog의 Diary에서는 댓글 조회·작성 모두 불가하다.

공개 콘텐츠는 발견 가능하게 열어 두되, 쓰기와 비공개 기록 관리에는 인증·소유권 검증을
강제한다.

## 4. 이미지 업로드와 전달

### 선업로드 흐름

이미지는 Diary 저장 전에 업로드하고, 정제 결과의 `objectKey`를 DiaryPage에 연결한다.
직접 URL 입력은 지원하지 않는다. 선업로드 후 사용되지 않은 파일의 자동 정리는 MVP
이후 개선 사항이다.

S3 객체는 전부 비공개로 유지한다. DB에는 영구 URL 대신 `objectKey`를 저장하고,
Diary/피드 API가 접근 권한을 판단한 후에만 presigned GET URL을 조회 DTO에 넣는다.
presigned URL은 저장하지 않는다.

공개 Diary도 S3 객체를 공개하지 않는다. 공개·비공개 접근 판단은 S3 ACL이 아니라
애플리케이션 계층에서 일관되게 수행한다. 이 방식은 비공개 기록의 URL 유출 위험을
줄이지만, URL 만료·재발급 UX를 별도로 다뤄야 한다.

### 클라이언트와 서버의 책임

- React 클라이언트는 HEIF/HEIC를 자동으로 JPEG로 변환해 호환성을 돕는다. 이 규칙은
  iPhone과 Android를 구분하지 않고 파일 형식에 적용한다.
- 클라이언트의 크기·형식 검사는 사용자 경험을 위한 보조 검증일 뿐 보안 경계가 아니다.
- 서버가 실제 형식, 바이트 크기, 해상도, 픽셀 수를 최종 검증한다.
- 서버는 EXIF 방향을 픽셀에 반영하고, 메타데이터를 복사하지 않은 새 JPEG를 만든다.
  GPS 등 원본 메타데이터가 S3에 남지 않게 하기 위함이다.

### 입력·정제 정책

| 단계 | 정책 |
| --- | --- |
| 서버 입력 형식 | JPEG, PNG, 또는 클라이언트가 JPEG로 변환한 HEIF/HEIC |
| 원본 상한 | 파일당 20MB, 최대 50MP, 각 변 최대 8,192px |
| 리사이징 | 종횡비 유지, 긴 변 최대 2,560px |
| 최종 형식 | JPEG, quality 0.85 |
| PNG 알파 | 흰 배경으로 합성한 뒤 JPEG로 저장 |
| 최종 안전 상한 | 단일 재인코딩 결과가 5MB 초과이면 거절 |
| S3 저장 대상 | 메타데이터가 제거된 정제 JPEG만 저장 |

원본을 넓게 수용한 뒤 한 번만 정제하면 스마트폰 사진 업로드 UX와 저장·전송 비용을
함께 관리할 수 있다. 3MB에 맞추기 위한 반복 품질 조정은 구현·테스트 복잡도에 비해
MVP 가치가 낮아 제외했다. 200MP 원본, 서버 HEIC 변환, 동영상 처리·트랜스코딩도
MVP에서 제외한다.

AWS S3는 최소 IAM 권한으로 접근하고, 월 $1 AWS Budget 알림과 비용 이상 탐지를
설정한다. CloudFront·Lambda 등 추가 인프라는 MVP 범위가 아니다.

## 5. MVP 제외와 이후 후보

- DiaryPage 동영상 업로드·재생·썸네일·트랜스코딩
- 200MP 이미지 처리
- 반복 JPEG 품질 조정
- 업로드만 되고 Diary에 연결되지 않은 S3 객체의 자동 정리
- Cursor 페이지네이션, 무한 스크롤
- Archive 상태, WalkParty, 알림, 채팅, 일반 Q&A/Post

이 항목들은 제품 방향 문서의 확장 후보일 뿐 현재 엔티티·ERD·API에 선반영하지 않는다.

이 문서는 기존 문서를 삭제·수정하지 않는다. 구현을 시작하기 전 아래 문서를 서로
일관되게 갱신해야 한다.

| 기존 문서 | 현재 내용 | 확정 설계와의 차이 |

## 7. 아직 결정되지 않은 설계 질문

1. 선업로드 objectKey의 소유권·단일 연결을 위해 최소 `MediaUpload` 추적 엔티티를 둘지,
   Member별 S3 key prefix 검증으로 시작할지
2. 업로드 API의 구체 계약: multipart 요청, objectKey·임시 미리보기 URL 응답, Diary 저장
   때 연결 검증과 실패 처리
3. presigned GET URL의 만료 시간과 프론트엔드 재발급 UX
4. Diary 제목을 MVP에 둘지, 첫 페이지 멘트 기반으로만 표현할지
5. 시/군/구 `regionCode`의 실제 코드 체계·데이터 소스·갱신 정책
6. 필드 제약, API 응답·오류 코드, 테스트 범위와 배포 환경별 S3 설정
